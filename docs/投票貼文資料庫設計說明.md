Easy Social 投票貼文資料庫設計說明

文件版本：1.0
撰寫日期：2026-05-25
適用系統：Easy Social（Flask + SQLAlchemy）
資料庫環境：SQLite（本機開發）與 PostgreSQL（Supabase 部署）

本文說明 Easy Social 系統中「投票貼文」功能的資料庫設計。投票貼文允許使用者發佈包含二至四個選項的問卷式貼文，其他使用者可以對其中一個選項投票。系統在使用者投票後，會統計各選項的票數與百分比，並將結果顯示於貼文介面中。

本設計採取擴充既有貼文模型的方式實作。也就是說，投票貼文仍然是貼文的一種，只是在原本的 post 資料表上增加辨識欄位，並另外建立 poll、poll_option 與 poll_vote 三個資料表來保存投票題目、選項與投票紀錄。這樣的設計可以讓一般文字貼文、媒體貼文、轉發貼文與投票貼文共用同一套貼文流程，同時又能維持投票資料的完整性。


一、設計目的

投票貼文功能的主要目標，是讓使用者能在社群平台中快速發起簡單投票。每則投票貼文包含一個問題與二至四個選項。登入使用者可以對每則投票選擇一個選項，且同一位使用者對同一則投票只能投一次。

在資料庫設計上，本功能需要滿足以下需求。第一，投票貼文必須能與既有 post 貼文資料整合。第二，每則投票需要保存多個選項，並保留選項顯示順序。第三，系統必須記錄每位使用者的投票行為，以防止同一使用者重複投票。第四，投票結果需要能有效率地統計票數與百分比，避免在動態牆載入多則貼文時產生過多查詢。


二、整體資料模型概念

Easy Social 原本已有 user 與 post 兩個核心實體。投票功能新增 poll、poll_option 與 poll_vote 三個實體後，整體關係如下。

User 與 Post：
一位使用者可以發佈多篇貼文，因此 user 與 post 是一對多關係。投票貼文也是 post 的一種，所以仍然透過 post.author_id 關聯到發文者。

Post 與 Poll：
一篇貼文最多只能對應一組投票。一般貼文沒有 poll 資料；投票貼文則會有一筆 poll 資料。因此 post 與 poll 是可選的一對一關係。

Poll 與 PollOption：
一則投票包含二至四個選項，因此 poll 與 poll_option 是一對多關係。每個選項會記錄文字內容與顯示順序。

Poll 與 PollVote：
一則投票可以收到多筆投票紀錄，因此 poll 與 poll_vote 是一對多關係。

User 與 PollVote：
一位使用者可以參與多則投票，因此 user 與 poll_vote 是一對多關係。不過，針對同一個 poll_id，同一個 user_id 只能出現一次，藉此確保一人一票。

PollOption 與 PollVote：
每一筆投票紀錄都會指向某一個選項，因此 poll_option 與 poll_vote 是一對多關係。


三、資料表設計

3.1 post 資料表

投票貼文仍然儲存在既有的 post 資料表中。投票問題文字放在 body 欄位，並透過 is_poll 欄位標記該貼文是否為投票貼文。

post 資料表主要欄位如下。

id：整數，主鍵，用來識別每一篇貼文。
body：文字，不可為空。一般貼文時代表貼文內容；投票貼文時代表投票問題。
media_filename：字串，可為空，用來儲存媒體檔名。投票貼文第一版不使用此欄位。
media_type：字串，可為空，用來記錄媒體類型。
is_poll：布林值，不可為空，預設為 false。用來標記貼文是否為投票貼文。
created_at：含時區的日期時間，不可為空，記錄貼文建立時間。
author_id：整數，不可為空，外鍵連到 user.id，代表發文者。
repost_of_id：整數，可為空，外鍵連到 post.id，用來表示轉發來源。

post 資料表保留內容檢查條件。每篇貼文至少需要符合下列其中一種情況：body 有內容、media_filename 有值、repost_of_id 有值，或 is_poll 為 true。這可避免產生完全空白且沒有意義的貼文資料。


3.2 poll 資料表

poll 資料表代表一則投票本身。每一筆 poll 都必須連到一篇 post，並且同一篇 post 最多只能有一筆 poll。

poll 資料表主要欄位如下。

id：整數，主鍵，用來識別每一則投票。
post_id：整數，不可為空，外鍵連到 post.id。此欄位具有唯一限制，確保一篇貼文只能建立一組投票。
created_at：含時區的日期時間，不可為空，記錄投票建立時間。

poll 資料表的 post_id 欄位需要建立唯一索引。如此一來，即使應用程式邏輯發生錯誤，資料庫層也能阻止同一篇貼文被建立多組投票。


3.3 poll_option 資料表

poll_option 資料表儲存投票選項。每一則投票會有二至四筆 poll_option。

poll_option 資料表主要欄位如下。

id：整數，主鍵，用來識別每一個選項。
poll_id：整數，不可為空，外鍵連到 poll.id，表示此選項屬於哪一則投票。
label：字串，不可為空，代表選項文字。
position：整數，不可為空，代表選項顯示順序，範圍為 0 到 3。

poll_option 資料表需要在 poll_id 上建立索引，以加速查詢某則投票的所有選項。此外，poll_id 與 position 組合需要唯一，避免同一則投票內出現重複的顯示位置。position 也需要檢查條件，限制其值必須大於等於 0 且小於 4，對應最多四個選項的位置。


3.4 poll_vote 資料表

poll_vote 資料表儲存使用者的投票紀錄。每一筆資料代表某位使用者在某則投票中選擇了一個選項。

poll_vote 資料表主要欄位如下。

id：整數，主鍵，用來識別每一筆投票紀錄。
poll_id：整數，不可為空，外鍵連到 poll.id，表示投票紀錄屬於哪一則投票。
option_id：整數，不可為空，外鍵連到 poll_option.id，表示使用者選擇了哪個選項。
user_id：整數，不可為空，外鍵連到 user.id，表示投票者。
created_at：含時區的日期時間，不可為空，記錄投票時間。

poll_vote 資料表需要在 poll_id、option_id 與 user_id 上建立索引，以支援投票統計與使用者投票狀態查詢。最重要的限制是 user_id 與 poll_id 的組合必須唯一，確保同一位使用者對同一則投票只能投一票。


3.5 user 資料表

user 資料表不需要為投票功能修改結構。投票功能會透過 post.author_id 找到投票貼文的發佈者，並透過 poll_vote.user_id 找到投票者。


四、外鍵關係說明

post.author_id 連到 user.id，表示每篇貼文的作者。
post.repost_of_id 連到 post.id，表示轉發貼文所參照的原始貼文。
poll.post_id 連到 post.id，表示一則投票屬於哪一篇貼文。
poll_option.poll_id 連到 poll.id，表示某個選項屬於哪一則投票。
poll_vote.poll_id 連到 poll.id，表示某筆投票紀錄屬於哪一則投票。
poll_vote.option_id 連到 poll_option.id，表示某筆投票紀錄選擇了哪個選項。
poll_vote.user_id 連到 user.id，表示某筆投票紀錄由哪位使用者產生。

這些外鍵關係可以確保投票資料不會脫離既有貼文與使用者資料而獨立存在。例如，投票紀錄必須指向有效的使用者、有效的投票，以及有效的選項。


五、業務規則與資料完整性

投票功能需要遵守以下業務規則。

第一，投票選項數量必須介於二至四個之間。此規則主要由應用程式層檢查，並透過 poll_option.position 的檢查條件輔助限制最多四個位置。

第二，同一則投票中的選項文字不可重複。為避免大小寫差異造成看似不同但實際相同的選項，應用程式會先正規化選項文字，再進行重複檢查。

第三，投票貼文必須有問題文字。建立投票貼文時，body 欄位不可為空。

第四，同一位使用者對同一則投票只能投一次。此規則由 poll_vote 資料表中的 user_id 與 poll_id 唯一限制保證。

第五，使用者投票時，選擇的 option_id 必須屬於該 poll_id 底下的選項。此規則由應用程式在寫入 poll_vote 前查詢驗證。

第六，投票百分比由選項票數除以總票數後乘以 100 得出。若總票數為 0，所有選項百分比皆為 0。

第七，若使用者轉發一篇投票貼文，投票統計仍然歸屬原始貼文。也就是說，轉發貼文只負責顯示原始投票內容，不會建立新的 poll。


六、典型資料流程

6.1 建立投票貼文

建立投票貼文時，使用者會提交貼文類型、投票問題與選項列表。系統會先驗證問題文字是否存在，並檢查選項數量是否介於二至四個之間。接著，系統會建立一筆 post 資料，將 is_poll 設為 true，並把 body 設為投票問題。

post 建立完成後，系統會新增一筆 poll，並透過 post_id 與該篇貼文連結。最後，系統會依照使用者輸入的順序建立多筆 poll_option，position 從 0 開始遞增。


6.2 使用者參與投票

使用者參與投票時，前端會送出使用者選擇的 option_id。後端收到請求後，會先確認使用者已登入，再確認該選項確實屬於該投票。若使用者尚未對此 poll_id 投票，系統會新增一筆 poll_vote。

投票紀錄寫入後，系統會重新統計該投票各選項的票數，並計算百分比。前端可以依照回傳結果更新畫面上的票數與比例長條圖，不需要重新整理整個頁面。


七、查詢與效能考量

在動態牆中，系統可能一次載入多則貼文，其中可能包含多則投票貼文。若每一則投票都個別查詢票數，容易產生 N+1 查詢問題。因此，投票統計應以批次方式處理。

較好的做法是先取得目前頁面上所有投票的 poll_id，再使用 poll_id IN 條件搭配 GROUP BY option_id 一次統計多則投票的票數。如此可以減少資料庫查詢次數，提升動態牆載入效率。

此外，在讀取貼文時，可以預先載入 Post.poll 與 Poll.options。這樣前端渲染投票貼文時，就不需要為每一篇貼文額外查詢投票選項。


八、應用程式模組對應

投票功能在程式中的責任分工如下。

easy_social/models.py：
定義 ORM 模型，包括 Poll、PollOption、PollVote，以及 Post.is_poll 欄位。

easy_social/poll_service.py：
負責投票相關商業邏輯，例如選項驗證、建立投票、寫入投票紀錄與統計投票結果。

easy_social/social.py：
負責 HTTP 路由，例如建立投票貼文與處理投票請求。

templates/social/_poll.html：
負責投票畫面的 HTML 結構與結果顯示。

static/js/app.js：
負責投票後以 JSON 回應即時更新畫面，讓使用者不需要重新整理頁面即可看到最新結果。


九、資料庫初始化與部署注意事項

本專案目前使用 db.create_all() 建立資料庫結構，尚未使用獨立 migration 檔管理 schema 變更。在本機開發環境中，可以執行 task init-db 建立 SQLite 資料庫。在 Supabase 部署環境中，可以執行 task setup-supabase 建立 PostgreSQL 資料表與 Storage bucket。

如果既有 SQLite 資料庫是在投票功能加入前建立的，舊資料庫中不會有 is_poll 欄位，也不會有 poll、poll_option 與 poll_vote 資料表。此時需要刪除舊的 SQLite 檔案並重新初始化，或手動執行 ALTER TABLE 與 CREATE TABLE 指令補上新結構。

在 production 環境中，若資料表尚未建立，使用者註冊、發文或投票時可能會出現資料表不存在的錯誤。因此部署後應確認資料庫初始化流程已執行完成。


十、邏輯資料模型文字圖

整體關係可以用文字方式表示如下：

使用者可以發佈多篇貼文。
一篇貼文可以是一般貼文，也可以是一篇投票貼文。
若貼文是投票貼文，該貼文會對應一筆投票資料。
每則投票包含多個選項。
每位使用者可以對多則投票投票，但對同一則投票只能投一次。
每一筆投票紀錄都會指向某一位使用者、某一則投票，以及該投票底下的一個選項。

換句話說，投票貼文的核心資料流是：

user 建立 post，post 對應 poll，poll 擁有 poll_option，user 透過 poll_vote 選擇其中一個 poll_option。


結語

本設計以最小幅度擴充既有貼文系統，讓投票貼文可以自然地融入 Easy Social 的動態牆、使用者貼文、轉發與互動流程。透過 poll、poll_option 與 poll_vote 三張新表，系統能清楚區分投票本身、投票選項與使用者投票紀錄。同時，透過唯一限制、外鍵限制與應用程式驗證，可以確保投票資料正確且不易產生重複或不一致的狀態。
